# 双周活动预告（本周五至下下周五）与登录维护

默认每双周周二北京时间 09:00（自 2026-11-24 起算，可通过仓库 `config/push.toml` 在 GitHub 网页直接调整）生成并发送至飞书群，方便「学术先锋号」推文同学在周四整理发布。主窗口为**本周五至下下个周五**（共 15 天，分为「第一周：本周五至下周四」与「第二周：下周五至下下周五」两段），本周五前紧急办理事项与下下周五之后的长期重要机会单列。例如 2026年11月24日（周二）生成的主窗口为 11月27日（周五）至 12月11日（周五）。

选择依据是活动时间、报名截止及原文有效性。较早发布但仍开放的机会保留，上期已经介绍但还没过期的机会会再次出现。本周五前就需要办理的单列，不会因主窗口从周五开始而漏掉周二至周四截止的通知。已结束、取消、暂缓、回顾及报名已截止的排除。

原文明示报名截止月日但未写年份时，只按同文已核验的活动年份归年，并展示截止原文与推定说明。跨年活动的上一年报名按日期顺序处理；多个不同截止无法确定时转待核实。同一天有明确截止时刻的，过时即排除。

公众号和官网原文日期须经过现有校验。就业官网活动使用明确的活动字段，报名资格仍看详情页。岗位刊登有效期不能代替企业实际投递截止，未核验正文的岗位单列为待核实，不计入已核验预告。主报告不设置固定条数上限；简短卡片放不下的内容保留在Word完整版。

每天仍持续采集与分拣；周二生成不依赖一次临时模型调用成功，模型可以补充优先级和复核意见，不能无声删除日期已经核验的机会。定时任务会发送飞书卡片和Word链接；公众号图文发布仍由负责人安排。同一群同一排期周期去重；回执未知时不盲目重发。

登录状态保存在服务器，会话每30分钟保活。微信读书在会话过期时自动尝试刷新并重放请求；公众号后台保活时保存续期Cookie。登录健康时维护页面显示“登录有效，无需扫码”，不会创建新的扫码任务。平台撤销会话、续期凭据无效或要求再次验证时，仍需本人扫码，不能承诺永久免扫码。二维码更新本身不等于完成本人授权。

所有会话和状态文件以bitfeed用户（UID994）读写，保持0600。状态不可读或损坏时停止，不初始化空状态覆盖原记录。软件升级不删除session.json，不重新关注已关注的公众号。

接口只看得到各号最新一篇，未来尚未发布的活动也无法预知。报告的“全部”指已取得并通过有效性核验的条目，不代表所有公众号历史、多图文或未公开安排均已覆盖。

## Cookie优先与可选搜号授权

已有登录先复用服务器Cookie，登录按钮先静默检查和续期；网络错误、限流或首页样式变化不直接触发新二维码。只有明确缺少或撤销了会话才进入扫码。首页样式变化时以自有账号列表核验，不单凭缺少旧页面字段就判断失效。

“格拉摩根的指挥官”仅为可选搜号授权：默认不因它过期推送扫码或恢复通知，打开维护页也不自动给它出码。已有公众号采集仍独立运行，微信读书采集失效或停滞的真实提醒保留。新增号优先粘贴其公开文章链接，无需自己的公众号后台登录；确需名称搜索才手动处理搜号授权。若某项运维任务确实依赖后台搜号，可设置BITFEED_MP_LOGIN_REQUIRED=true重新启用该项提醒。平台撤销会话后，旧Cookie不能恢复被撤销的权限。
